# Create or Adapt a Project Vault

Part of [[Jobs/Jobs]]. Use only for an assigned creation/adaptation. This procedure does not authorize moving existing material, rewriting other vaults, provisioning tools or starting a runtime.

1. Verify project purpose, owner, destination and local location instructions. Check destination contents; do not overwrite or merge an unrelated vault. Preserve existing canonical homes. Keep one live home for each project and respect the explicit destination.
2. Reuse current project contracts. Create only a map, agent contract, current-state/ownership note, plan registry/template, needed Jobs and handoff structure. Add actual workstream notes only when work exists. Keep private source material out.
3. Separate observed truth, proposed architecture, approved scope and human acceptance. Latest uses explicit registry links, with immutable full snapshots when a plan is formally revisioned.
4. Put the **architecture ambiguity review** in the local plan Job, proposal template and agent-entry instructions. Verify the routes are accessible inside this vault; avoid broken cross-vault links.
5. Verify identity, renamed paths, links, optional catalog routes and the first real workstream's stable ID/canonical vault ID. Follow [[Reference/Workstream Routing]] for verified local discovery and entry pointers within authorized scope; otherwise report pending installation. Read back created files. No application suite, provider call or automated reviewer is implied by setup.
6. Record the meaningful setup handoff with what was created, checked and pending. Do not claim installation, enforcement or universal adoption from documents.

## Architecture ambiguity requirement

Every architectural draft, review, amendment and revision includes:

| Decision boundary | How an agent could drift | Explicit direction and section | Owner / verification | Status |
| --- | --- | --- | --- | --- |

Statuses are **Resolved**, **Deferred outside active increment**, or **Needs decision**. Put binding direction beside the relevant contract and use this table as an index. Resolve every consequential active-increment choice or explicitly remove it from that increment before declaring implementation readiness. A genuinely missing decision means not ready. Future deferrals need an activation condition and grant no current scope. Leave routine compatible methods to the builder.

Use relevant lenses: outcome versus methods; decision/state ownership; interaction entry/target binding; schemas/identities; context storage/retrieval/correction/forgetting; model/access/spending; failure/recovery/Stop; scope/order; migration/compatibility; finite acceptance/rollback. This protects outcomes and authority without creating unnecessary intake or repeated approval questions.

**Teaching example only — not a recorded project decision:**

| Decision boundary | How an agent could drift | Explicit direction and section | Owner / verification | Status |
| --- | --- | --- | --- | --- |
| Which note owns active claims? | Copy the board into every workstream, causing conflicting owners | The canonical board is Current State; workstreams link it. See the entry contract's Coordination section. | Setup reviewer opens both routes and finds one board | Resolved for the template's documentation pattern |

During setup, ask the onboarding agent to explain this row and identify an analogous boundary in the real assignment. Do not save it as an approved architecture decision. Completion means entry, plan template and plan Job all reach this framework, links resolve and existing material is preserved.
